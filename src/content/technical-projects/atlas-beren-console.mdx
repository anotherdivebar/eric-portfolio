## Overview

Atlas-Beren Console is the internal control plane behind managed workflow installs. It is for me as the operator, not a customer portal. It manages client workspaces, agent rollout, data intake, approvals, integration status, value and risk surfacing, and Atlas-Beren's own prospecting pipeline in one system.

Operator loop: `Today -> client workspace -> readiness -> agent run -> approval -> client action`

## Problem

One operator juggling clients, agents, data intake, approvals, integration health, and new-business pipeline work does not need another disconnected stack of spreadsheets, dashboards, and one-off scripts. The problem was keeping the expensive gaps visible: stale follow-up, missing readiness, integration drift, unapproved actions, and prospecting work with no next step.

## Approach

The console is catalog-driven. Agents are not just names and prompts; they carry runbook fields for value, KPIs, evidence, and anti-promises. Client workspaces track data sources, unified profiling, readiness gates, approvals, activity, and client actions after approval. Prospect Finder lives in the same system, so customer acquisition is not a side spreadsheet.

## What shipped

- **Client workspaces** with per-client agents, CSV and unified profiling intake, evidence and readiness gates, activity log, approvals, and post-approval client actions.
- **Agent catalog (30+)** grouped for operators across data/readiness, client ops, revenue/growth, prospecting, and governance/cost - including Prospect Finder as a client-assignable agent.
- **Operator Today** ranking client ops, agent failures, approvals, integration health, prospect follow-ups, and stale data in one morning inbox.
- **Integrations control panel** with env-based masked status for AI Gateway, GCP/Vertex, Places, Hunter, HubSpot, n8n webhooks, GCS, and cron/RSS feeds - no secrets pushed into the browser.
- **Prospect Finder** for Places discovery, AI briefs, optional enrichment, pipeline/deals, and approval-first outbound with org-level pipeline attribution.
- **Governance layer** with human approval for external actions, mock versus live runs, readiness overrides logged, and estimated versus verified value guardrails.
- **Owner visibility** with the same queues feeding status, risk, and next-action views instead of rebuilding the picture by hand.

## Architecture

Supabase handles auth, role-gated access, RLS, and Postgres-backed state. Vercel deployment and cron handle scheduled checks and lightweight monitoring. Integration state stays metadata-first and env-backed. Live agent execution can route through the AI Gateway, while optional GCP services cover heavier document and model workflows when needed.

## Lessons learned

- Evidence before live runs matters more than another "agent" headline.
- Human approval is not a limitation; it is the difference between a usable operator system and a risky toy.
- Integration health should surface where the operator starts the day, not as a buried settings page.
- Metadata-first rollout beats pretending you already have a mature secret and orchestration layer.
- Prospecting and recovery work better when they live inside the same system as readiness, review, and next action.

## What is next

- Per-client Finder partitioning so prospecting views can split more cleanly by account context.
- Live integration probes beyond env and metadata checks.
- Encrypted secret registry once the current env-based pattern stops being the right tradeoff.
